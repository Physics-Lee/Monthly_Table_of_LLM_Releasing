半自动发布更新实现计划

给执行者：实现本计划时，请按任务逐项执行，并在每个任务后运行对应验证命令。

目标：构建一个半自动工作流：脚本自动发现大模型发布候选项，人类审核确认后，再通过现有 data.json 更新链路写入正式表格。

架构：继续保持 data.json 作为唯一真源。新增候选发现层，把尚未审核或尚未应用的数据写入 pending-releases.json；再新增一个应用脚本，复用现有的 upsert、build、check 逻辑。GitHub Actions 可以按需或定时运行发现流程，但只生成可审核结果，不静默修改正式表。

技术栈：Node.js 20、现有 CommonJS 脚本、GitHub Actions、JSON 文件、现有 scripts/upsert-entry.js、scripts/build-json.js、scripts/check-data-links.js。

前提假设

  • 第一版不直接用脆弱的 HTML 解析去抓所有厂商网站。
  • 第一版只支持少量明确配置的数据源，优先选择稳定的官方 RSS、Atom 或 API。
  • 候选项必须经过人工批准后，才允许进入 data.json。
  • 现有表格列是权威列；未知厂商只报告，不自动新增列。
  • 正式数据的修改仍然通过现有单条更新链路完成。

成功标准

  • 运行一个命令即可生成包含候选发布的 pending-releases.json。
  • 运行一个命令即可校验候选文件，并报告缺字段、重复模型、未知厂商、已收录条目。
  • 被批准的候选项可以写入 data.json，无需手工编辑整张表。
  • 应用候选项后，CSV、MD、links.json 会自动重建，且 check-data-links.js 通过。
  • GitHub Actions 可以手动或定时运行发现流程，并产出可审核的 PR 或 artifact。

步骤 2：实现应用脚本

node scripts/apply-release-candidates.js pending-releases.json

行为：

  • 读取候选文件。
  • 先运行候选校验。
  • 对每个 approved 候选项调用 scripts/upsert-entry.js 导出的 upsertEntry()。
  • 顺序处理候选项，不并发写 data.json。
  • 成功应用后标记为 applied。
  • 写回更新后的候选文件。
  • 运行或提醒调用者运行 node scripts/check-data-links.js。

保持简单，不做数据库锁、队列或复杂冲突处理。

步骤 3：添加 dry-run 模式

任务 6：添加 GitHub Actions 发现流程

  • 修改：.github/workflows/build.yml

步骤 1：先做手动触发 workflow

name: Discover Releases

on:
  workflow_dispatch:

jobs:
  discover:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: node scripts/discover-releases.js --sources scripts/sources.json --out pending-releases.json
      - run: node scripts/check-release-candidates.js pending-releases.json
      - uses: actions/upload-artifact@v4
        with:
          name: pending-releases
          path: pending-releases.json

第一版不做什么

  • 不做完整浏览器自动化。
  • 不做基于 LLM 的无人自主判断。
  • 不自动创建厂商列。
  • 不在没有人工批准时自动发布。
  • 不抓取私有、付费墙或需要登录的来源。
  • 不做复杂去重，只做精确匹配或简单归一化匹配。
